### D.1 The core data model & representation

- **A two-level split: opaque handles over dense indices.** The public surface (`Net`, `Place`, `Transition`, `Marking`, `PetriNet<N>`) sits over an index-based core (`DenseNet`, `IdxMarking<T>`, `DenseMapping`, `UniqueSortedSlice`). `DenseNet` holds four boxed adjacency arrays of presorted slices plus precomputed structural facts — `class: NetClass`, `is_strongly_connected: bool`, and `preset_t / postset_t / preset_p / postset_p` (`core/net.rs:28-43`), described as *"The structure of a Net compressed into a packed format optimized for analysis"* (`core/net.rs:26`). Both the class and strong-connectivity are computed **once at build time** and read by analysis as O(1). *Open question:* this is a deliberate "pay once, query cheaply" design — how much of the eventual performance story lives in this precomputation versus in the algorithms downstream?

- **`UniqueSortedSlice<T>` is the concrete substance behind "cache-friendly."** A write-once, deduplicated, sorted `Box<[T]>` whose invariants hold by construction (`core/unique_sorted_slice.rs:8-9, 21-44`), exposing `is_subset_of` / `intersects` / `is_disjoint` as O(n+m) merge scans over the sort order (`:69-110`). Presets and postsets are contiguous ordered integer arrays. (This is the structure the README's "cache-friendly data structures" performance claim, `README.md:22`, appears to be pointing at — worth confirming with Michael.)

- **A marking is a dense `Box<[T]>`, generic over token type** (`core/marking.rs:10-11`), default `u32`, indexed directly by `PlaceIdx` (`:95-106`). Markings carry a componentwise partial order — `partial_cmp` folds elementwise comparisons through `merge_ordering`, returning `None` (incomparable) when some components go each way (`:139-158`). This lattice is what Karp–Miller acceleration and coverability rest on.

- **The topology is stored twice.** `Net` wraps the cache-friendly `DenseNet` *and* a redundant `petgraph::Graph<Node, ()>` *and* the `DenseMapping` (`api/net/mod.rs:72-99`) — once as four presorted index slices, once as a bipartite petgraph (used for circuit/SCC algorithms). *Open question:* what governs which representation an analysis reaches for, and is the duplication a settled boundary or a transitional state as algorithms migrate between the two?

- **A single generic explorer abstracts the token domain via `TokenOps`.** The same `DenseStateGraphExplorer<'a, T>` serves `u32` reachability and `Omega` coverability (`core/state_space/mod.rs:25-31, 54`). *Open question:* is `IdxMarking<T>` the intended seam for further generalization (weighted arcs, capacities, "unbounded systems"), or is the unweighted ordinary-net case expected to stay fixed?

- **The verdict vocabulary is rich and ordered.** `NetClass` is an explicit 6-variant **diamond** lattice (`Circuit, StateMachine, MarkedGraph, FreeChoice, AsymmetricChoice, General`; the `enum` spans `core/class.rs:17-396`) with hand-written `matches!` subclass predicates collected in one `impl` block (`is_circuit`, `is_state_machine`, `is_marked_graph`, `is_free_choice`, `is_asymmetric_choice` at `core/class.rs:401-431`), where `StateMachine` and `MarkedGraph` are incomparable. `Boundedness` is a two-variant enum carrying the bound, totally ordered so every finite bound sits below `Unbounded` (`core/boundedness.rs:7-46`). `LivenessLevel` is the full Murata L0–L4 hierarchy with `Ord` matching liveness strength (`core/liveness.rs:5-71`, citing *"Murata 1989 §V-C"*). *Note on connectivity:* `classify` returns `None` for nets that fail a **weak**-connectivity check — an undirected BFS over the bipartite graph asserting the *underlying undirected* graph is connected (`core/class.rs:498, 504-524`), with the comment *"this library only supports connected nets."* Note that this is distinct from **strong** connectivity, which is computed and stored *separately* (`is_strongly_connected`) and is what several structural shortcuts actually gate on. The distinction is load-bearing in the theory: many S-net/T-net liveness and reachability theorems are stated for *strongly* connected nets. *Open question:* where does each shortcut need *weak* vs. *strong* connectivity, does the single build-time weak-connectivity gate match the preconditions of the shortcuts that fire downstream, and how does "connected nets only" interact with what MCC/PNML inputs actually present?

### D.2 The state-space exploration engine

- **One generic engine; two token types; one structural difference.** Reachability (`T = u32`) and coverability (`T = Omega`) share the entire fire/register/search machinery; the *only* behavioral difference is one extra step injected by the `Omega` path: **`omega_accelerate`** (Karp–Miller ω-acceleration), a nested fn inside `ExploreNext<Omega>::explore_next` (`core/state_space/coverability.rs:189-214`). After firing, it walks **all ancestors** of the source node and promotes every strictly-greater component to `Omega::Unbounded`. The `u32` path has no such step. *This single inserted call is what makes coverability terminate on unbounded nets.* The module doc cites Primer Prop 3.23 and Esparza Thm 3.2.5 for termination (`api/state_space/coverability.rs:8, 11`). One half-sentence worth having ready if the conversation goes deep: the reason Karp–Miller halts at all is the **well-quasi-ordering** of markings (Dickson's lemma on ℕᵏ) — ω-acceleration is what forces the WQO's finite-antichain property to actually terminate the BFS, and it's the thing an examiner tends to probe.

- **Boundedness is decided by the absence of ω.** `CoverabilityGraph::is_bounded` is literally `!...node_weights().any(IdxOmegaMarking::has_omega)` (`api/state_space/coverability.rs:137-140`); place bounds fold the componentwise max into `Bounded(k)` / `Unbounded` (`:159-177`).

- **A short-circuit that avoids completing the coverability graph.** `try_build_reachability_graph` (`api/state_space/coverability.rs:93-106`) drives exploration and bails the instant a *newly discovered* marking shows ω (`if is_new && ...has_omega() { return Err(self); }`). On success it promotes the ω-free graph to a `ReachabilityGraph`. The cost model is documented: for bounded nets the cost equals building the reachability graph; for unbounded nets you avoid completing the full coverability graph (`api/system/mod.rs:281-294`). *Open question:* the promotion is currently a copy guarded by `unreachable!` with a self-flagged `// todo: this creates a new graph, can we reuse the old one instead?` (`coverability.rs:198`). Is "the coverability graph of a bounded net *is* its reachability graph" something Michael wants to make a type-level/zero-copy fact, or is copy-and-assert adequate?

- **Liveness L0–L4 comes from reachability-graph SCCs, and the code argues its own limits.** `liveness_levels` runs `tarjan_scc` and classifies transitions (`core/state_space/reachability.rs:39-109`, cited to Murata §V-C). The L4 predicate is "for every SCC, the transition labels an internal edge OR the SCC has an external outgoing edge" (`reachability.rs:77-83`) — i.e. *t* must appear in every **terminal (bottom) SCC*. The elegance worth being able to articulate: terminal SCCs are exactly the recurrent classes — the markings the system can be trapped in forever — so "fireable from every reachable marking" (L4) reduces soundly to "present in every bottom SCC." The code also carries a multi-line argument that **L2 cannot exist without unboundedness**, so on a finite state space L2 collapses into L1/L3 — ending with `// todo: how to detect L2 without trying to construct an infinite state space?` (`:105`). *Open question:* this is one of several places where the code marks the exact spot where finite-state reasoning runs out and structural reasoning would have to take over. (A sharper sub-question, if it interests Michael: does the terminal-SCC test handle a deadlock state — a trivial bottom SCC with no enabled transition — as the same object the deadlock detector at `core/state_space/mod.rs:321-331` finds?)

- **The explosion-mitigation surface is dedup + Karp–Miller, and nothing else (yet).** There is no partial-order/stubborn-set reduction, no symmetry reduction, no symbolic (BDD/SAT) representation in this engine. Increment/decrement are unit-weighted (`*self += 1` for `u32` at `core/state_space/reachability.rs:10`; `*n += 1` for `Omega` at `core/state_space/coverability.rs:126`), applied by the generic `fire()` at `core/state_space/mod.rs:159-164`; `is_enabled` only checks `at_least_one` (`mod.rs:149-152`) — no weighted arcs, inhibitors, capacities, or resets. *Open question:* where, if anywhere, does Michael see "high performance" grounded relative to that absence — in the structural shortcuts that let many nets **skip** search entirely, in something inside the explorer, or somewhere else?

- **Frontier seeding is a sound over-approximation.** `potentially_enabled_transitions` unions postsets of marked places with always-on source transitions, candid that this *"allows us to avoid iterating over all transitions"* and rechecks real enablement on pop (`core/state_space/mod.rs:111-127, 149-152`). BFS gives shortest firing sequences (`api/state_space/mod.rs:307-311`). Deadlock detection is purely topological — nodes with no outgoing edge (`core/state_space/mod.rs:321-331`).

### D.3 Structural analysis (proving without search)

- **A one-sided, conservative contract.** This is the polynomial "fast path": settle properties by inspecting structure (incidence, siphons, traps, LP relaxations) instead of building a state space. The recurring shape: each check **either returns a definite verdict with a named witness or yields `None`/inconclusive and defers to search** — so the structural layer is never wrong, only silent. The `.ok().map(|_| true)` idiom across liveness/boundedness/deadlock-freedom encodes exactly this (success proves the property; failure proves nothing).

- **Siphons and traps by greatest-fixpoint shrinking.** `maximal_siphon_in` / `maximal_trap_in` iteratively remove offending places (`core/analysis/siphon_trap.rs:15-39, 49-78`, cited to *Primer Algorithm 6.19*, O(|S|²·|T|²)). `minimal_siphons` is the only *live* enumerator (backtracking with subset-domination pruning, `:82-123`); its three siblings — `minimal_traps`, `minimal_siphons_ilp`, `minimal_traps_ilp` — are fully written but carry `#[expect(unused)]` (`:131, :183, :244`). *Open question:* two complete strategies for the same objects (fixpoint vs. ILP) coexist with the ILP variants dead — is the choice between them (net size? density? structure?) itself something the thesis might characterize empirically?

- **The marking-equation filter proves UNREACHABLE only.** Solving `m₀ + N·x = m'` for non-negative `x`: *"if no solution exists, m' is definitely not reachable… If a solution exists, reachability is possible but not guaranteed (the equation ignores firing order)"* (`core/analysis/semi_decision.rs:6-10, 62-106`). Infeasibility short-circuits to a named `UnreachabilityProof`; feasibility falls through to coverability (`api/system/reachability.rs:172-187`). It runs a rational-then-integer ladder with a self-flagged `// todo: only test ILP if the rational solution is already an integer solution` (`:180`).

- **Commoner–Hack is the single shortcut reused across three properties.** `commoner_hack_criterion` folds over minimal siphons, computing the maximal trap inside each and checking it is marked (`siphon_trap.rs:370-394`); it returns `Ok(all witness pairs)` or `Err(first counterexample siphon)`. The same call drives **free-choice liveness** (`api/system/liveness.rs:110`), **deadlock-freedom** (`api/system/deadlock_freedom.rs:41`), and **asymmetric-choice / live-free-choice boundedness** (`api/system/boundedness.rs:70`). The doc states the necessary-and-sufficient (free-choice liveness) vs. sufficient-only (general deadlock-freedom) split (`siphon_trap.rs:330-369`). *Connected observation:* the refactor gave this its own module whose *return type is the evidence* — `api/system/chc.rs` defines `SiphonTrapPair { siphon, trap }` and `CommonerHackCriterionResult = Result<Box<[SiphonTrapPair]>, UnmarkedSiphonTrapPair>`, carrying every minimal siphon paired with its maximal contained trap on success or the first counterexample siphon on failure, with the nec.-and-suff. vs. suff.-only distinction stated on the type itself (`chc.rs:8-39`). This is a concrete instance of the proof-carrying idea (E.3): the witness *is* the API surface, not a side channel.

- **Structural boundedness is a positive S-place-invariant inequality, deliberately weaker than conservativeness.** `find_positive_place_subvariant` looks for `y >> 0` with `yᵀN ≤ 0`, explicitly *"weaker than conservativeness (which requires yᵀ·N = 0)"* (`semi_decision.rs:253-274`, citing Murata Table 5 / Primer Prop 4.12). *A small terminology note to raise lightly, not correct:* the code's coined term "sub-invariant" is, in the classical Murata/Esparza vocabulary, usually the place **super-invariant / S-surinvariant** (the `≤ 0` case yields an *upper bound* on the weighted token sum), as opposed to an S-invariant proper (`= 0`). Since the thesis will be read by people fluent in that vocabulary, a tiny open question is whether Michael wants the public naming to track the literature — minor, but exactly the kind of precision an advised reader rewards.

- **P/T-invariants are documented at length but never implemented — and the doc links dangle.** `literature.rs:195-228` describes conservativeness, consistency, S- and T-invariants; but **no `Invariants` type, no `compute_invariants`, no `structural` module exist** anywhere in the crate. The links to `structural::compute_invariants`, `Invariants::is_covered_by_s_invariants`, `structural::commoner_hack_criterion_inner` (`literature.rs:207, 221, 228, 71, 104, 298`) point at symbols that aren't there. *Open question:* invariants are the classical bridge between the marking equation and structural reasoning — what role would a real `compute_invariants` play next to the existing LP filters, and would it move any verdict from *one-sided* to *positively structural*?

- **A ready primitive with no callers.** `has_unmarked_circuit` is an O(n+m) DFS for a zero-token directed cycle, with the documented meaning that *"In a strongly connected marked graph, such a circuit implies the net is not live"* (`api/net/path.rs:188-238`). Grep finds **no callers.** This is more pointed than "an unused helper" once you name the underlying theorem: for marked graphs, **Commoner's liveness theorem** says a marked graph is live iff *every* directed circuit carries ≥1 token under M₀ — and crucially, circuit token-count is a conserved quantity (a T-invariant-flavored fact) in marked graphs, so checking "every circuit marked" *at the initial marking alone* decides liveness with no search. Under that reading, `has_unmarked_circuit` is not just a witness but a **complete decision procedure** for the marked-graph liveness arm, already written and simply not dispatched. Meanwhile that arm currently returns a fixed answer (next subsection). *Open question:* does Michael see this DFS as the canonical structural witness/decider for the T-net case, and how does it relate to the siphon/trap machinery — two proofs of the same fact, or different facts?

- **Two-sided structural verdicts already exist for state machines.** For S-nets, unequal token sums give a *negative* proof (`StateMachineTokenConservation`); equal sums in a strongly connected S-net give a *positive* one (`LiveStateMachineTokenConservation`, Theorem 5.1.5) (`api/system/reachability.rs:143-156`). *Open question:* for which other net classes does a *two-sided* structural reachability verdict exist in the theory, and where could that boundary be drawn in this dispatch?

**E.1 Structure vs. search.** The whole library is organized as "try a polynomial structural argument keyed on `NetClass`; fall back to state-space exploration only when it yields `None`." ## G. FALSIFIABILITY SCAFFOLDING

These are **generic frames** for turning *any* chosen direction into a testable claim. They do **not** choose the claim — they're the shape a claim takes once Michael has one. Offer them when he's ready to sharpen, not before.

For whatever direction Michael leans toward, you can help him fill in:

- **The one-sentence claim.** "This thesis demonstrates that ____." Force it to be a *single declarative sentence* with a subject that could, in principle, be false.

- **What would prove it wrong.** The most useful question. If the claim is "structural shortcuts decide a large fraction of real nets cheaply," the falsifier is "on the MCC corpus, the fraction is small / the structural path isn't cheaper than search." If the claim is "proof-carrying verdicts are checkable and useful," the falsifier is "the certificates can't be independently verified / don't help a user." If "guided/selected search beats baseline," the falsifier is "it doesn't beat the obvious ordering." A claim with no conceivable falsifier isn't yet a thesis claim — it's a description.

- **Does it preserve exactness — and is that the right trade?** A frame that applies to *every* direction, not just one: does the proposed work keep the tool's current soundness (every answer exact and certificate-backed), or does it trade some of it? If it trades exactness, what is gained in return, and what would falsify that the trade was worth it? If it *preserves* exactness (e.g. a guidance layer that only orders/selects over exact deciders), then "could it be wrong?" simply isn't a live objection — say so, and don't import it. Posing this uniformly keeps any single direction from looking uniquely risky.

- **The baseline.** Every performance or coverage claim needs a *comparison*. Against what? (Another MCC tool? petrivet's own search path without the structural tier? The naive all-transitions frontier vs. the over-approximation at `core/state_space/mod.rs:111-127`? The existing Criterion benches as a starting point? Last year's MCC results?) Name the baseline explicitly; "faster" and "better" are not claims until there's a "than what."

- **The minimal falsifiable version.** What is the *smallest* experiment or artifact that could already support or refute a scaled-down version of the claim? (e.g. "on N free-choice MCC models, the CHC path returns a verdict in polynomial time where search times out" — a small, runnable, honest first result that the differential harness plus the benches could produce now.) Building the minimal version early is usually worth more than perfecting the maximal one late.

- **The unit of evidence.** Is the evidence a *benchmark table* (time/coverage on a corpus), a *proof/construction* (a theorem that the certificates are sound and checkable), an *artifact* (a usable tool with a user-facing story), or a *characterization* (a map of which net classes get which verdicts on real data)? Different directions produce different *kinds* of evidence; naming the kind early shapes the whole back half of the thesis.

Use these as a checklist *with* Michael once he has a candidate direction — not as a gate he must pass to be allowed to explore.
